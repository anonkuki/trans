# 翻译系统提速与工作电脑落地方案

## 一、目标与边界

本方案用于解决长文档翻译等待时间过长的问题。当前电脑只负责形成可复用代码、自动化测试和配置模板，不连接测试或正式服务器，不写入生产密钥，也不替代工作电脑上的发布验证。

第一阶段采用低风险调度优化：小文档并发 12、中文档并发 10、大文档并发 8，并将单个 Java 进程的模型调用总并发限制为 24。自适应功能在代码中默认关闭，必须在工作电脑测试环境显式启用，避免仅替换 JAR 就改变旧环境行为。第二阶段再评估相邻段落批量翻译、文本层 PDF 快速路径和持久化缓存。

## 二、实测基线

同一个小样本每档预热 1 次、正式运行 3 次：

| 并发 | 平均耗时 | 相对并发 1 加速 |
|---:|---:|---:|
| 1 | 93.144 秒 | 1.00x |
| 6 | 26.853 秒 | 3.47x |
| 8 | 21.815 秒 | 4.27x |
| 12 | 18.370 秒 | 5.07x |

并发 6 调至 8 在该样本上提速约 19%；并发 6 调至 12 提速约 32%。长文档曾在并发 8 时出现上游读取超时，因此不能对所有文件固定使用 12。

## 三、已实现的动态并发

系统在创建文档线程池前统计有效翻译片段数与总字符数：

| 文档级别 | 判定条件 | 每文档并发 |
|---|---|---:|
| 小 | 片段数不超过 30，且字符数不超过 8,000 | 12 |
| 中 | 未达到小文档条件，且未超过大文档阈值 | 10 |
| 大 | 片段数超过 150，或字符数超过 50,000 | 8 |

实际线程数还会被待翻译任务数和全局上限约束。只有 5 个片段时，即使小文档目标值是 12，也只创建 5 个工作线程。

所有真正的 `ChatModel.call` 共用公平信号量，默认每个 Java 进程最多同时执行 24 个远程模型请求。因此两名用户同时上传小文档时，不会无限叠加为不受控线程。

注意：该全局上限是“单 JVM 上限”。如果生产环境有多个后端实例，需要按实例数量拆分额度，或在网关/Redis 增加分布式限流。例如总额度希望为 24、有 3 个实例时，可先将每个实例配置为 8。

## 四、工作电脑推荐配置

测试环境第一轮使用：

```env
TRANSDOC_ADAPTIVE_CONCURRENCY_ENABLED=true
TRANSDOC_CONCURRENCY=6
TRANSDOC_SMALL_CONCURRENCY=12
TRANSDOC_MEDIUM_CONCURRENCY=10
TRANSDOC_LARGE_CONCURRENCY=8
TRANSDOC_SMALL_SEGMENT_THRESHOLD=30
TRANSDOC_SMALL_CHARACTER_THRESHOLD=8000
TRANSDOC_MEDIUM_SEGMENT_THRESHOLD=150
TRANSDOC_MEDIUM_CHARACTER_THRESHOLD=50000
TRANSDOC_GLOBAL_CONCURRENCY=24
TRANSDOC_TRANSLATION_MAX_ATTEMPTS=2
```

`TRANSDOC_CONCURRENCY=6` 是关闭自适应后的回退值。密钥仍由服务器环境变量或配置中心注入，不放入仓库、JAR 或前端。

## 五、工作电脑验证步骤

1. 拉取 `integration/system1-pdf-ocr` 分支，复制服务器现有配置并单独备份旧 JAR。
2. 在测试环境配置上述变量，确认 Qwen、PaddleOCR、Redis、Nacos 和数据库连接正常。
3. 使用同一份基准文档分别运行旧 JAR 和新 JAR，至少重复 3 次；不要用不同文档比较速度。
4. 分别测试小文档、完整 SOP、扫描 PDF，以及两名用户同时提交任务。
5. 核对输出段落数、表格行列数、数字/单位、错误数和人工翻译抽检，不以“速度快”代替质量验收。
6. 观察 429、超时、重试率、模型调用峰值、CPU、内存和任务等待时间。
7. 测试环境连续稳定后再手动替换正式环境 JAR；保留上一版本以便回滚。

建议日志至少记录：任务 ID、文档片段数、字符数、选择的文档并发、全局等待时间、OCR 耗时、模型耗时、重试次数、失败片段数、总耗时。

## 六、验收标准

- 同一样本 3 次运行的中位数相较旧版本下降至少 15%。
- 译文段落、表格、数字、单位及文档标识符不低于旧版本质量。
- 单任务最终错误片段为 0；发生瞬时超时后可以重试恢复。
- 两名用户并发提交时，不出现进程崩溃、线程无限增长或模型接口持续 429。
- 大文档耗时波动可解释，并且任务进度持续更新。

## 七、回滚

无需回退代码即可恢复原固定并发：

```env
TRANSDOC_ADAPTIVE_CONCURRENCY_ENABLED=false
TRANSDOC_CONCURRENCY=6
TRANSDOC_GLOBAL_CONCURRENCY=6
```

修改配置后重启后端。若仍有异常，恢复备份的旧 JAR 和原配置。

## 八、后续提速阶段

第一阶段只能减少调度等待，预计对小文档提升约 15%～35%。要把长文档从约 8～9 分钟进一步压缩到约 3～5 分钟，下一阶段应按以下顺序实施：

1. 每次向 Qwen 提交 4～6 个相邻段落，以稳定 JSON ID 映射返回；失败批次自动拆成单段重试。
2. 检测 PDF 文本层，原生文本页直接解析，只有扫描页调用 PaddleOCR。
3. 对页眉、页脚、表头、固定术语和重复句建立持久化翻译缓存。
4. 根据 Qwen 私有云实测吞吐和首 Token 延迟重新标定全局并发，而不是沿用公网 API 参数。

批量翻译会改变段落请求协议，必须单独做格式、数字和错位回归测试，不与本次低风险动态并发修改混为一次生产发布。
